# Transaction and FHE latency

> Historical design / QA record. Dates, test counts, images, balances and open
> branches below describe that run. For the current player flow, deployment and
> sponsor behavior, see [Current Ashenkin release](current-state.md).

Scope: optimize the existing wallet flow, preserving signing authority, actual receipt/proof checks, Sepolia contracts, motion and mobile layout. No new transaction, fee bump, migration, deployment or wallet delegation is part of this change.

Baseline evidence:
- `tacticsSettle` awaits an optional wild-plan private read after the settle receipt, before returning the public result. Its private retry sleeps alone can total 57.364 seconds; UI still says waiting for a block.
- Receipt probe: PublicNode 187/85ms and Tenderly 433/278ms, both successful for fight #20's settled transaction. dRPC rejects both requests with code35: Sepolia is unavailable on its free plan.
- Receipt polling already uses one confirmation, 2 seconds. Keep that confirmation requirement and replacement detection. Improving RPC observation cannot make Sepolia produce blocks faster.
- Public/private decrypt retries sleep even after their final failed attempt, and retry permanent errors. Concurrent identical calls are not coordinated. SDK initialization is lazy and can start on the first action.

Implementation and acceptance:
1. Test the real settlement path: a pending optional private read must not delay a confirmed battle result; malformed public round responses must never reach signing. Preserve explicit wild-plan reading in the log.
2. Race two bounded RPC receipt observers (one signed submission only); keep the other observer alive if one fails, abort unused polling, retain repriced transactions and reject cancelled/replaced calls. Remove unavailable dRPC and reduce transport failover time. Keep wallet fee choice unchanged.
3. Share identical in-flight decryption requests within public/private/account/key contexts. Retry transient failures, stop invalid-signature/config/input errors, and never sleep after the final attempt. Keep attempts bounded and proof verification intact. Prewarm FHE after a valid wallet connection without signatures; use the same fallback RPC for SDK reads.
4. Distinguish receipt-confirmed processing from waiting for a block. Show time in the current step separately from total action time.
5. Focused failing tests before implementation, then all frontend tests/type-check/build. Read-only live receipt/public-result verification in Chrome; do not trigger a new wallet signature or transaction.

References: [viem receipts](https://viem.sh/docs/actions/public/waitForTransactionReceipt), [fallback transports](https://viem.sh/docs/clients/transports/fallback). Checked installed viem and relayer SDK types before changing APIs.

Verified implementation:
- Confirmed settlement returns its public round result immediately; private wild-plan reading remains an explicit battle-log action. Missing or malformed round bits stop before signing.
- Two receipt observers share one signed submission, retain one required confirmation, handle repricing/cancellation, and abort unused polling. The unavailable dRPC endpoint is removed; transport timeouts are bounded at 4 seconds.
- FHE initialization warms after a connected Sepolia wallet without requesting a signature. The SDK uses the bounded fallback provider. Identical in-flight decrypt calls share work, with private calls isolated by account and authorization context. Permanent failures stop early; retries never sleep after the final attempt. No persistent proof cache was introduced.
- The scene separates confirmed receipt processing from block waiting and displays current-step and total elapsed time.

Validation (2026-11-14):
- Frontend: `bun test tests` — 79 passed, 0 failed, 566 assertions across 20 files. Focused regressions were observed failing before implementation. `npm run type-check` and `npm run build` passed; build retains the existing large-chunk advisory.
- Live read-only receipt lookup for settled fight #20: first available observer returned success in 180ms; a controlled primary-observer failure still allowed the real secondary RPC to return success in 224ms. Both matched transaction `0x6e4db9d611d199daa7a9c128612c373c835b044faadb1c9cd762f87def21fe33`, block 12128761. These measure fetching an already-mined receipt, not new block inclusion.
- Chrome: clicked **Verify all three rounds** for fight #20 using the actual SDK/provider/KMS path. The UI reported **All three KMS results match Sepolia**, all three rounds Challenger, with a nonempty KMS proof. Success was observed within 6.4 seconds of clicking (includes time between browser tool calls; not a precise service benchmark). Screenshot: `../tmpshots/latency-proof-20.jpg`.
- No new transaction, wallet signature, fee change, contract deployment, dependency or delegated wallet authority was used. A newly submitted transaction's inclusion time and before/after end-to-end latency remain unmeasured. Sepolia block production and Zama coprocessor availability remain external limits.
